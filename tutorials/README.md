## What changed from the inference-only tutorial

The previous notebook (`TASK-INFERENCE`) reranked three synthetic candidates for one synthetic query and reported a `not-measurable` verdict because the repository shipped no metric and the sample had no relevance labels. This notebook keeps the reranking contract as Section 5 (on a Banking77 test shortlist instead of the synthetic sample) and adds the adaptation contract around it: a real labelled corpus with seeded hard-negative shortlists, ranking recall@k and MRR in the carried `metrics.py` with a random floor and a lexical baseline as reference points, a bounded listwise fine-tuning of the last decoder layers, before/after orderings, and an artifact that reloads. The per-batch `evaluation_report` still returns `not-measurable`; `pipe.evaluate` is the labelled corpus-level stage (`measured` / `measured-small-sample`).

## Conformance notes

- **Standalone carrier (ST1–ST8):** the primary path performs no clone, repository install, or repository import. Section 2 embeds the repository's 3 modules verbatim in topological dependency order (each tagged `metadata.dimer.embedded_module`; the only rewrites make `DEFAULT_WEIGHTS_DIR` working-directory-relative and remove internal relative package imports), Section 3 carries the 13-file snapshot manifest inline and asserts it against the module's constants before fetching, and `NOTEBOOK_SOURCE` records the repository, revision and module digests in the exports.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried modules, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD9):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries a fresh clone lacks (the git-ignored `model.safetensors`), at the pinned revision; `verify_snapshot` re-hashes every entry; `Qwen3RerankerPipeline.from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files (`local_files_only=True`, `trust_remote_code=False`) and cross-checks the `yes`/`no` token ids; no cell outside the carried modules calls `huggingface_hub`, `transformers`, `safetensors`, `urllib` or the model directly.
- **Data (DAT1–DAT9, ST6):** the default sample is two pinned objects — `train.csv` / `test.csv` of Banking77 (839,073 / 239,961 bytes; SHA-256 `b06e26ac…` / `d12d6e3b…`) from `raw.githubusercontent.com` at the pinned `PolyAI-LDN/task-specific-datasets` commit — each refused on any mismatch before it is parsed, turned into `{id, query, positive, negatives}` records whose positive is the intent name as words and whose negatives are a seeded shortlist (`sample_negatives`), de-duplicated on the message, and drawn by a seeded balanced shuffle into 231 / 77 / 154 records from the release's own train/test members (`check_split_disjoint` asserts it). The template adds a second *External access* bullet naming the host, the byte counts and the CC BY 4.0 licence.
- **Stages (§4.1):** `fetch_corpus` + `read_corpus` + `build_sample_dataset` / `load_byod_dataset` + `split_dataset` (sample acquisition) → `validate_dataset` + `check_split_disjoint` + refusal probes (validation, with three digests) → `validate_inputs` + `pipe.rerank` on one shortlist with sanity checks and the frozen orderings of three shortlists (inference contract) → `random_floor` + `pipe.lexical_baseline` + `pipe.evaluate` on the frozen model (floor, baseline and frozen) → `pipe.adapt` (bounded listwise fine-tuning) → `pipe.evaluate` on validation and test with the comparison (evaluation) → `pipe.rerank` after adaptation + `evaluation_report` (inference) → `pipe.save_artifact` → `Qwen3RerankerPipeline.from_artifact` with the parity assertion (export and reload).
- **Score semantics (UNC1–UNC4):** the relevance score is the `yes` share of a two-way softmax, not a calibrated probability, and not comparable across the frozen and adapted models; recall@k and MRR are ranking metrics over the dataset's own shortlists with ties counted against the positive; no acceptance threshold ships.
- **Baselines and evidence (EVAL6/EVAL10/EVAL11):** the random floor, the lexical baseline and the frozen model are scored on the same 154 shortlists as the adapted model, the query counts are asserted equal, `median_rank` is printed beside every mean, and every metric is labelled as one seeded split and shortlist construction of one corpus with no dispersion estimate; the notebook states that the adapter changes the shared decoder layers, prints the gold score before and after, and presents orderings as observations, not evidence.
- **Split integrity (SPL1–SPL8):** the split is seeded, balanced over the 77 intents and query-disjoint (the release's own train/test partition); validation selects the epoch and the test split is used for nothing but the final evaluation; the notebook states that queries from one user or session must be split by that grouping.
- **Ceilings (VAL6):** `MAX_PAIRS` (32), `MAX_TEXT_TOKENS` (8,192, truncated longest-first and flagged at inference), `MAX_TEXT_CHARS` (100,000), `MAX_TRAIN_TOKENS` (192, training-only truncation), `MAX_TRAIN_CANDIDATES` (4), the record bounds (8..20,000), the negatives bounds (1..15) and the id pattern are stated in the Prerequisites and printed before the model runs; four dataset refusals and one pair refusal are demonstrated.
- **BYOD (DAT10–DAT19):** `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog; when enabled, user records and the caller's `INSTRUCTION` flow through the same validation, seeded query-disjoint split, floor and baseline, frozen scoring, fine-tuning, evaluation, reranking, export and reload cells. The expected schema and the privacy guidance — an internal query log with its relevance labels is restricted data — are stated in the Prerequisites and in Section 4, and the training split is written to `outputs/qwen3_reranker_train.csv` in that shape.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded clean run in `../docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`.
